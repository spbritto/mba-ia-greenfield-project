       77 +                                                              
       78 +### phase-03-videos/TD-01                                     
       79 +                                                              
       80 +**Recommendation:** BullMQ                                    
          +on Redis is the most battle-tested Node.js queue, with        
          +first-class NestJS integration via `@nestjs/bullmq`           
          +(`BullModule.forRoot()`, `@Processor()`, `@InjectQueue()`)    
          + and the broadest official documentation                      
          +. Redis runs as a dedicated `redis` service in `compose.yaml` 
          +(with `appendonly yes` so queued jobs survive a container     
          +restart),                                                     
          +which makes the queue an explicit infrastructure component —  
          +the Phase 03 acceptance criteria require object storage, queue
          + and worker to come up via Docker Compose alongside the       
          +backend. Option A was set aside because the                   
          +BullMQ 6 PostgreSQL backend is very recent (                  
          +`bullmq` 6.0.0 published on npm on 2026-07-30                 
          +), its `@nestjs/bullmq` `backendFactory` integration could not
          + be confirmed in official documentation                       
          +, and it would leave no dedicated queue service in Compose.   
          +Option C's NestJS integration is a low-adoption               
          +community package.                                            
       81 +                                                              
       82 +**Libraries:** bullmq, @nestjs/bullmq                         
       83 +                                                              
       84 +### phase-03-videos/TD-02                                     
       85 +                                                              
       86 +**Recommendation:**                                           
          +The API generates lightweight presigned URLs; the actual 10GB 
          +transfer goes directly from the client to MinIO/S3, leaving   
          +the NestJS process completely                                 
          +unloaded. For files >5GB, the API orchestrates the S3         
          +multipart upload flow                                         
          + (generate upload ID + presigned URLs per part), and the      
          +client uploads parts in parallel directly to storage.         
          +This is the standard pattern used by YouTube, Vimeo, and every
          + production video platform.                                   
          +Option B (tus) adds infrastructure complexity that is         
          +not justified when the storage already                        
          +supports resumable multipart uploads natively. Option C is    
          +explicitly disqualified by the project requirements.          
       87 +                                                              
       88 +**Libraries:** —                                              
       89 +                                                              
       90 +**Revisions:**                                                
       91 +- 2026-11-13 — Presigned URLs handed to clients are signed    
          +against a separate public storage endpoint                    
          +(`S3_PUBLIC_ENDPOINT`, e.g. `http://localhost:9000` in local  
          +dev), while server-side S3 calls (API and worker) use the     
          +internal Compose endpoint (`S3_ENDPOINT=http://minio:9000`).  
          +Tests that run inside the `nestjs-api` container set          
          +`S3_PUBLIC_ENDPOINT` to the internal endpoint so they can     
          +reach the URLs. Rationale: the S3 signature covers the host,  
          +so a URL signed for `minio:9000` is unusable outside the      
          +Docker network; this is the only place a non-service host     
          +appears and it is never used for container-to-container       
          +traffic (root `CLAUDE.md` → Docker Networking).               
       92 +- 2026-11-13 — The bucket CORS policy allows                  
          +`PUT`/`GET`/`HEAD` from the client origin and exposes the     
          +`ETag` response header. Rationale: the client must read each  
          +part's `ETag` to complete the multipart upload.               
       93 +                                                              
       94 +### phase-03-videos/TD-03

          + S3 in production. AWS SDK v3 is the canonical S3 client,

          +feature coverage, and is MinIO-compatible via `endpoint` +    
          +`forcePathStyle`. Only two packages are adopted:

      100 +### phase-03-videos/TD-04                                     
      101 +                                                              
      102 +**Recommendation:** The worker runs as a dedicated            
          +`video-worker` service in `compose.yaml`, matching the        
          +architecture diagram (Video Worker as its own container) and  
          +the Phase 03 acceptance criteria, which require the worker to 
          + come up via Docker Compose alongside the backend. The        
          +shared-code concern is resolved without duplication: both     
          +services are built from the same `nestjs-project/` codebase,  
          +and the worker has its own entrypoint that boots a NestJS     
          +application context (no HTTP server) registering only what it 
          + needs — the `@Processor()` for the video-processing queue,   
          +the storage service and video persistence — while the API     
          +process does not register the processor. The image used by    
          +the worker includes the FFmpeg binaries (`ffmpeg`,            
          +`ffprobe`). FFmpeg is invoked directly through                
          +`node:child_process` (`spawn` of `ffprobe` to read duration   
          +and stream metadata as JSON, and of `ffmpeg` to extract a     
          +single frame as the JPEG thumbnail); `fluent-ffmpeg` is not   
          +used because the package is deprecated on npm ("Package no    
          +longer supported"). The worker reads the source video from    
          +storage through a presigned GET URL (FFmpeg reads HTTP inputs 
          + using range requests), avoiding a full local copy of files   
          +up to 10GB. Options A and C were set aside because they leave 
          + no worker service in Compose.

      110 +### phase-03-videos/TD-05                                     
      111 +                                                              
      112 +**Recommendation:** A single, universal code path eliminates  
          +branching and ensures 10GB support from day one. The          
          +multipart flow with parallel part uploads is strictly         
          +superior in throughput and resilience for any file over       
          +~100MB, which is the typical video file range. The            
          +client-side complexity is bounded and well-documented (S3     
          +multipart presigned is a standard pattern). Option B's dual   
          +path adds maintenance cost for a marginal simplicity win on   
          +small files that is rarely exercised (video files are         
          +typically >100MB).                                            
      113 +                                                              
      114 +**Libraries:** —                                              
      115 +                                                              
      116 +**Revisions:**                                                
      117 +- 2026-11-13 — Upload limits and contract: fixed part size of 
          + 100 MiB (last part may be smaller); maximum file size of 10  
          +GiB (10 × 1024³ bytes), validated at initiation against the   
          +declared size and again at completion against the stored      
          +object size (`HeadObject` `ContentLength`); accepted content  
          +types `video/mp4`, `video/webm`, `video/quicktime`,           
          +`video/x-matroska`. Part URLs expire after 1 hour and the     
          +owner can request fresh URLs for specific part numbers while  
          +the video is `draft`; the owner can abort an in-progress      
          +upload (`AbortMultipartUpload`). Rationale: the 10GB limit    
          +comes from the project plan, and the S3 limits (5 MiB minimum 
          + part, 10,000 parts maximum) are satisfied with ~103 parts at 
          + 10 GiB; validation found these parameters unspecified.       
      118 +                                                              
      119 +### phase-03-videos/TD-06                                     
      120 +                                                              
      121 +**Recommendation:** The use case is a YouTube-like URL        
          +identifier: short, URL-safe, shareable, non-sequential.       
          +_Adjusted during review (2026-11-12):_ the identifier uses    
          +the NanoID URL-safe alphabet (`A-Za-z0-9_-`) with a fixed     
          +length of **12 characters**, generated with Node's built-in   
          +`node:crypto` (`randomBytes(9).toString('base64url')`, 72     
          +bits of entropy, no padding) instead of the `nanoid` package  
          +— current `nanoid` releases are ESM-only (`"type":            
          +"module"`), while the backend compiles to CommonJS and runs   
          +tests under ts-jest. This also removes a dependency.          
          +Uniqueness is guaranteed by a `UNIQUE` constraint on the      
          +column plus regenerate-and-retry on collision. YouTube uses   
          +an 11-character base64 identifier, so 12 characters keeps the 
          + same aesthetic. The internal primary key stays a UUID; the   
          +short ID is only the public URL identifier. CUID2's           
          +distributed anti-collision guarantees add unnecessary         
          +complexity for a single-Postgres deployment. UUID is too long 
          + for user-facing URLs.

      125 +### phase-03-videos/TD-07                                     
      126 +                                                              
      127 +**Recommendation:** Same architectural principle as TD-02:    
          +offload byte transfer from the API. S3/MinIO handle range     
          +requests natively, so HTTP streaming "just works" when the

          + enforced at the URL generation endpoint). Option B

          +visibility feature doesn't require a proxy; short-lived       
          +presigned URLs with DB checks suffice.

      129 +**Libraries:** —                                              
      130 +                                                              
      131 +**Revisions:**                                                
      132 +- 2026-11-13 — HTTP contract: `GET /videos/:publicId/stream`  
          +and `GET /videos/:publicId/download` respond `302 Found` with 
          + `Location` set to a presigned GET URL; the download URL sets 
          + `ResponseContentDisposition: attachment`. Presigned GET URLs 
          + expire after a configurable TTL (default 4 hours).           
          +Rationale: a redirect lets a `<video src>` or download link   
          +point at the API while the bytes (including `Range` requests  
          +answered with `206 Partial Content`) flow directly from       
          +storage.                                                      
      133 +- 2026-11-13 — Access rules: the owner of the video's channel 
          + can read metadata, stream and download in any status; anyone 
          + else, including anonymous users, only when the status is     
          +`ready`. A non-owner request for a video that is not `ready`  
          +returns 404 (existence is not disclosed). Rationale:          
          +anonymous viewing is a platform rule (project overview; Phase 
          + 05), while visibility controls are Phase 04 scope.           
      134 +                                                              
      135 +### phase-03-videos/TD-08                                     
      136 +                                                              
      137 +**Recommendation:** The presigned URL upload model            
          +(TD-02/TD-05) means the API has no visibility into upload     
          +progress — it only knows when the upload is initiated (draft  
          +created) and when the client confirms completion. An          
          +`uploading` state would require polling storage to verify     
          +progress, adding unnecessary complexity. Four states          
          +(including `failed`) are sufficient: `draft` covers the       
          +entire upload period, `processing` covers job execution,      
          +`ready` is the terminal success state, and `failed` enables   
          +retry. Stale drafts (abandoned uploads) can be cleaned by a   
          +periodic job that deletes `draft` videos older than a         
          +configurable TTL (e.g., 24h).                                 
      138 +                                                              
      139 +**Libraries:** —                                              
      140 +                                                              
      141 +**Revisions:**                                                
      142 +- 2026-11-13 — Failure policy: a processing job is attempted
